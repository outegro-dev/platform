# Исполнение одной задачи

## 1. Взять ограниченный пакет

Вход: task ID, карточка, её depends_on, контракты, исходное дерево. Не брать следующую задачу только потому, что текущая сложная. Для большой карточки использовать checkpoints внутри неё. Сессия модели может закончиться между checkpoints; фиксировать resume point в отчёте.

## 2. Проверить готовность

- Найти фактические артефакты всех hard dependencies. Статус done без отчёта недостаточен.
- Проверить внешние inputs. Если они нужны только для real-provider проверки, продолжить local/fake часть, но не закрывать внешнюю проверку.
- Прочитать boundary задачи. Не редактировать другой сервис для обхода отсутствующего контракта.
- Проверить git diff/неотслеживаемые файлы и не перетирать чужие изменения. Git ещё может не существовать до BOOT-01.
- Записать ожидаемые файлы и tests до реализации. Если фактическое дерево отличается, обновить mapping в отчёте.

## 3. Выполнять checkpoints

**C1: контракт и reproducer.** Описать input/output, ошибки и инварианты. Для исправления поведения получить failing meaningful test. Для UI подготовить проверяемые состояния. Для документации сравнить источники, не писать тест ради повторения текста.

**C2: минимальный рабочий путь.** Реализовать только позитивный сценарий карточки, затем сразу добавить negative/duplicate/ownership paths. Не оставлять фальшивый success в UI.

**C3: проверка и интеграция.** Выполнить все TC-ID. Проверить логи на секреты, совместимость зависимых contracts, EN/RU. Полный проект собирать, если затронут общий package или это release gate; иначе достаточно целевых checks плюс зависимые consumers.

**C4: передача.** Записать файлы, команды, реальные результаты, ограничения и следующий шаг. Статус done только с выполненными обязательными критериями. Отрицательный тест считается успешным, когда система правильно отказала, а не когда сам тест упал.

## 4. Статусы

`planned` → `in_progress` → `review` → `done`. `blocked` требует конкретного отсутствующего input/решения и перечисления завершённой независимой части. `deferred` — условная функциональность вне текущего выпуска. `failed` применяется к конкретному test run, а не вместо причины блокировки.

Статус карточки и task-index.json меняются вместе. Обновление task status — факт работы, не новый источник продуктовых решений. Все стартовые карточки planned, wallet deferred.

## 5. Неизвестное поведение

Если библиотечная сигнатура неизвестна — Context7 по AGENTS.md. Если provider response неизвестен — fixture со статусом synthetic и отдельная contract-validation задача. Если бизнес-решение неизвестно — прочитать open-inputs и использовать только явно записанный default. Для денег, ролей и внешней публикации не выдумывать потерянный результат.

## 6. Команды

До BOOT-04 нельзя считать `pnpm test:integration` существующей командой. BOOT-04 создаёт и документирует command map. Исполнитель сначала читает package.json соответствующего workspace и запускает реальные команды. Документационные утилиты из tools/documentation работают сейчас; они проверяют только документацию.

## 7. Ограничение контекста модели

Context helper печатает карточку и ссылки, а с `--bundle` добавляет только обязательные shared docs. Не прикладывать весь monorepo или все главы сразу. Если задача не помещается в контекст, остановиться на checkpoint и сохранить handoff: что сделано, что проверено, незавершённый шаг, точные файлы. Никогда не сокращать тесты финансовой целостности ради контекста.
