## Пошаговое выполнение

### C1. Подготовить контракт и проверку

Записать input/output, ожидаемые ошибки, затронутый инвариант, файлы и способ проверки. Для поведения использовать meaningful failing case/fixture; для визуального решения — конкретный preview; для документации — source comparison. Проверить реальные package scripts через [command map](../../../05-quality/command-map.md).

### C2. Реализовать ограниченный результат

1. Описать LoginChallenge с hash/expiry/attempts/consumedAt и neutral response. **Контроль:** сохранить конкретный diff/артефакт этого шага; сверить с контрактом и связанными TC ниже перед переходом дальше.
2. Реализовать start/resend/verify с атомарным consume и несколькими rate-limit keys. **Контроль:** сохранить конкретный diff/артефакт этого шага; сверить с контрактом и связанными TC ниже перед переходом дальше.
3. Подключить delivery port с fake для тестов; очищать plaintext после передачи. **Контроль:** сохранить конкретный diff/артефакт этого шага; сверить с контрактом и связанными TC ниже перед переходом дальше.
4. Создавать verified user/session только после успешной проверки и зафиксировать audit без кода. **Контроль:** сохранить конкретный diff/артефакт этого шага; сверить с контрактом и связанными TC ниже перед переходом дальше.

### C3. Проверить

Пройти все TC этой карточки. Важен конечный business state, а не только HTTP 200. Для изменённого shared contract запустить проверки его consumers. Не заменять реальные DB concurrency tests моками. Все обращения к внешним provider в обычном CI — fake; real-provider evidence отдельно. Прочитать diff на secrets/лишние изменения.

## Тест-кейсы

### TC-ID-01-01: Одноразовый код

- **Дано:** Валидный challenge.
- **Действие:** Дважды verify одним кодом.
- **Ожидается:** Первый вход успешен, второй отклонён без новой сессии.
- **Доказательство:** записать фактическое состояние/response/DB assertion или screenshot в test report. Для негативного сценария проверить также отсутствие запрещённого side effect.
- **Стартовый статус:** not-run.

### TC-ID-01-02: Expiry

- **Дано:** Clock после expiresAt.
- **Действие:** Verify правильный код.
- **Ожидается:** Код отклонён, сессия не создана.
- **Доказательство:** записать фактическое состояние/response/DB assertion или screenshot в test report. Для негативного сценария проверить также отсутствие запрещённого side effect.
- **Стартовый статус:** not-run.

### TC-ID-01-03: Перебор

- **Дано:** Неверные коды до лимита.
- **Действие:** Проверить следующий запрос.
- **Ожидается:** Rate limit действует; ответ не раскрывает наличие email.
- **Доказательство:** записать фактическое состояние/response/DB assertion или screenshot в test report. Для негативного сценария проверить также отсутствие запрещённого side effect.
- **Стартовый статус:** not-run.

### TC-ID-01-04: Конкуренция

- **Дано:** Два verify одновременно.
- **Действие:** Выполнить запросы через барьер.
- **Ожидается:** Только один consume; plaintext отсутствует в logs.
- **Доказательство:** записать фактическое состояние/response/DB assertion или screenshot в test report. Для негативного сценария проверить также отсутствие запрещённого side effect.
- **Стартовый статус:** not-run.
