# ADR-004: центральный вход и refresh

Status: **accepted для refresh-ротации** (28.09.2026, реализовано в `apps/auth-backend/src/sessions/refresh-store.ts`); SSO wire-протокол для нескольких клиентов (ID-04) — proposed, решается вместе с id-web.

## Refresh: принятая модель

Access-токен: JWT ES256, 5 минут, `sub`, `sid`, `roles`, `av`, JWKS на `/.well-known/jwks.json`. Refresh-токен: непрозрачный `<sid>.<256 бит>`, хранится только sha256. Состояние одной семьи в Valkey:

| Ключ | Значение | TTL |
|---|---|---|
| `rt:<sid>` | hash `{ cur: sha256(текущий) }` | срок refresh (30 дней) |
| `rtg:<sid>` | `sha256(предыдущий):текущий токен` | окно повтора (20 с) |

Одна атомарная Lua-операция на предъявленный токен:

| Предъявлен | Исход | Действие |
|---|---|---|
| текущий | OK | новый текущий, старый записан в окно повтора |
| предыдущий, окно живо | RETRY | возвращается уже выданный новый токен, новой версии нет |
| иное при живой семье | REUSE | обе записи удаляются, сессия в БД отозвана (`reuse_detected`), событие `identity.session.revoked.v1`, пользователю security-уведомление |
| семьи нет | DEAD | 401 |

Сценарии из refresh-spike: две вкладки и потерянный ответ → RETRY (тот же токен); два процесса синхронизируются атомарностью скрипта в одном Valkey; атакующий повтор вне окна → REUSE; logout/revoke удаляют семью, поэтому последующий refresh — DEAD. Окно 20 с покрывает параллельные вкладки и клиентский повтор с таймаутом до 10 с; меняется только через `REFRESH_GRACE_MS` с тестом. Открытый текст текущего токена живёт в Valkey не дольше окна, никогда не логируется.

Revoke побеждает: в самом Identity каждый запрос с access-токеном проверяет существование `rt:<sid>` (хук `isSessionActive`), поэтому revoke-all действует немедленно. Другие сервисы принимают access-токен до его истечения (≤ 5 мин); чувствительные команды перепроверяют права свежо (admin — по БД).

Проверки: TC-ID-03-01…04 в `apps/auth-backend/src/sessions.test.ts`.

## SSO между приложениями (ID-04, открыто)

Цель прежняя: id.outegro.dev, зарегистрированные клиенты, точные redirect, короткий одноразовый code + state + PKCE, обмен через BFF, host-only cookies, refresh только на сервере. Библиотеку/собственный ограниченный flow выбрать до подключения второго фронтенда; не называть собственный flow OIDC без соответствия.
