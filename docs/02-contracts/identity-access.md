# Identity и доступ

## Политика

Identity отвечает за человека, способы входа, sessions и административные roles. Payments отвечает за коммерческие grants. Resource owner проверяет `resource.userId === authenticatedUserId` либо отдельное разрешённое admin действие. Paid/pro никогда не означает admin.

## Defaults и точки проверки

| Последний способ входа | Удаление Google или passkey отклоняется (409 `last_method`), если не остаётся пригодного способа: подтверждённый email (код приходит на этот адрес), привязанная identity, passkey текущего RP | ID-02, ID-05 |

## Admin permissions

Owner имеет системные административные полномочия, но проходит sensitivity/step-up/audit. Support по умолчанию users.read(redacted), sessions.revoke, passkeys.revoke (снять passkey пользователя при потере устройства, с причиной), notifications.read/retry обычных сообщений. Billing operator billing.read, subscriptions.cancel; refunds.request отдельное назначение. Ручные коммерческие grants (выдать или отозвать доступ без оплаты) — grants.assign, по умолчанию только owner. Auditor только чтение audit/финансов в scope. Service operator services.read/allowlisted flags и operational replay без произвольного финансового command. Мониторинг (Grafana на `admin.outegro.dev/grafana/`) — monitoring.read, по умолчанию у owner, auditor и service operator: роль owner входит в Grafana как Admin, остальные с monitoring.read — как Viewer ([контракт входа](../06-operations/grafana-sso.md)). Обучение ([глава 17](../01-specification/chapters/17-education.md)): edu.read — книги, читатели и прогресс, аудит и вычитка любой книги, включая черновики (owner, support, edu_editor); edu.manage — статус и правило доступа книги с причиной (owner, edu_editor). Роль edu_editor ведёт учебники; чтение платных глав читателями — гранты Payments (`edu/library`, `edu/book.<slug>`), не роль. Кошелёк ([контракт](wallet.md), ADR-011): wallet.read — обзор, кошельки, журнал «было → стало», сверка и аудит; wallet.adjust — начислить и списать грамблсы с причиной, лимитом на операцию и аудитом. Оба по умолчанию только у owner: billing operator и auditor получают их только явным назначением, баланс грамблсов — не право и не роль (INV-08). Рулетка ([ADR-012](../03-decisions/adr/012-roulette.md)): roulette.read — живой стол, раунды, игроки, бонус дня, состояние сервисов (owner, support); roulette.manage — лимиты стола, пауза ставок, режим обслуживания, таблица бонуса дня с причиной (owner); roulette.void — аннулировать раунд с возвратом всех ставок (только owner). Балансы грамблсов правит раздел «Кошелёк» (wallet.adjust), не рулетка. Atelier ([ADR-013](../03-decisions/adr/013-atelier.md)): atelier.use — вход на atelier.outegro.dev и работа со своими вакансиями, CV и откликами; пока только у owner.

OAuth-клиенты приложений (`OAUTH_CLIENTS` auth-backend): pay-web, admin-web, battleship-web, edu-web; redirect — точный `https://<поддомен>/auth/callback`. Сайт-портфолио — тоже клиент: landing-web, redirect `https://outegro.dev/auth/callback`. Страницы сайта одинаковы для всех и сессию не читают; аккаунт в шапке браузер запрашивает после загрузки у `GET /api/account` того же origin (`{ name, email, roles }` или `null`, `Cache-Control: private, no-store`; 503 — Identity недоступна, шапка тогда предлагает «Войти»), там же обновляется сессия. В production у landing-web нет адресов по умолчанию: `APP_URL`, `ID_URL` и `AUTH_API_URL` задаются вместе (SSO включён) или не задаются вовсе (SSO выключен: тихого входа нет, `/api/account` и `/auth/*` отвечают 404); только часть из трёх или неверное значение валит `/health`, и под не становится ready. Неверный `GTM_ID` выключает только статистику. Порядок выкатки: landing-web в production `OAUTH_CLIENTS` auth-backend, затем id-web, затем landing-web с этими переменными; `tools/ops/smoke.mjs` проходит `/auth/sign-in` до `/authorize` и проверяет, что id знает клиента.

У unknown permission отказ. RoleBinding включает scope/expiry; последнее owner binding защищено транзакционно. Критичный доступ перепроверяется свежо, stale JWT role не основание для возврата или назначения owner. Самопроизвольный impersonation отсутствует.

## Тихий вход (silent sign-in)

Человек вошёл на id.outegro.dev и впервые открывает battleship.outegro.dev: приложение подхватывает вход само, без кнопки «Войти» (баг #107). У каждого приложения по-прежнему своя host-only сессия `og_at`/`og_rt` через свой PKCE flow; тихий вход — тот же flow без страницы входа (OIDC `prompt=none`).

- **Подсказка `og_hint`.** Пишет только id-web: значение `1`, Domain — родительский домен хоста `ID_URL` (id.outegro.dev → `outegro.dev`; на localhost и IP — host-only, cookies не различают порты), Path `/`, HttpOnly, Secure по HTTPS, SameSite=Lax, Expires — срок refresh-токена сессии id. Пишется при входе (код, passkey, Google) и при каждой ротации в proxy id-web; удаляется при выходе на id, при отказе refresh и когда запрос к id-web пришёл без сессии, а подсказка есть. Это не учётные данные и не основание для доступа: подделка даёт один лишний круг через /authorize, удаление выключает тихий вход. Сессия id без подсказки (вошедшая до выкатки) получает её на первом же запросе к id-web: proxy один раз ротирует ещё свежий токен, чтобы узнать срок сессии. Пока человек не открыл ни одной страницы id (включая `/authorize` после «Войти» в приложении), подсказки нет.
- **Маркер `og_silent`**, host-only у каждого приложения, HttpOnly, значения:
  - `tried` — ставит `/auth/sign-in` при тихой попытке, на 5 минут; на сутки, если попытка кончилась отказом, который повторится (`invalid_request`, отказ в обмене кода), а не отсутствием сессии id или сбоем;
  - `out` — на год: выход в приложении (`/auth/sign-out` battleship-web и landing-web, server action `signOut` edu-web) или отказ Identity в refresh (сессию отозвали, аккаунт заблокирован). Снимается только входом, о котором человек попросил;
  - `silent` — сессия приложения появилась тихо (см. выход на id).

  Пока маркер `tried`, `out` или незнакомое значение, тихого входа нет: петли невозможны, выход и отзыв молча не отменяются. Сессия приложения, истёкшая сама, при живой сессии id подхватывается снова.
- **Выход на id** убирает подсказку. Сессию приложения, появившуюся тихо (`og_silent=silent`), приложение заканчивает само на первом запросе без подсказки (`refreshSession` с `silent`: `POST /v1/sessions/logout`, cookies сессии и маркер удаляются): на общем компьютере следующий человек не увидит чужой аккаунт. Сессии, в которые человек входил сам, живут до выхода в них: глобальный выход вне scope.
- **Proxy приложения** (`silentSignIn` из `@outegro/bff/proxy`; battleship-web, edu-web и landing-web) начинает, только если у приложения нет сессии (`anonymous` или `signed-out`, не `unavailable`; landing-web не обновляет сессию в proxy и считает «нет сессии» только при отсутствии и `og_at`, и `og_rt`), есть `og_hint`, `og_silent` нет или `silent`, запрос — GET-навигация документа верхнего уровня (`Sec-Fetch-Mode: navigate` и `Sec-Fetch-Dest: document`; без Fetch Metadata — `Accept: text/html`), не prefetch или prerender (`Sec-Purpose`, `Purpose`), не бот по User-Agent, путь не `/auth/*` и не `/api/*`. Ответ — 303 на `/auth/sign-in?returnTo=<путь и query>&silent=1` с `Cache-Control: private, no-store`. Без подсказки не происходит ничего: анонимы и crawlers ничего не стоят, SEO не меняется. POST, server actions, переходы роутера (fetch) и API не перенаправляются никогда.
- **`/auth/sign-in?silent=1`** перепроверяет `og_hint` и `og_silent` (иначе 303 обратно на `returnTo`), `returnTo` проходит `safeRedirectPath` (длиннее 1024 символов — без query, ещё длиннее — стартовая страница: `og_sso` должен уместиться в 4 КБ); дальше обычный PKCE с `prompt=none` и `og_silent=tried`.
- **id `/authorize` с `prompt=none`.** Клиент и redirect_uri проверяются реестром как обычно; запрос, который реестр отклонил, заканчивается страницей «ссылка недействительна», без редиректа. Другие значения `prompt` игнорируются, как любой незнакомый параметр. С сессией id код выдаётся как обычно. Без сессии или при 401 — `redirect_uri?error=login_required&state=…`, при ином отказе — `invalid_request`, при сбое Identity — `temporarily_unavailable`. Если недоступен сам реестр, ответ уходит только на точный callback приложения или сайта из конфигурации id-web (`SITE_URL`, `PAY_URL`, `BATTLESHIP_URL`, `EDU_URL`, `ADMIN_URL` + `/auth/callback`), иначе страница ошибки. Эти решения — чистые функции `apps/id-web/src/lib/authorize.ts` (`parseAuthorizeRequest`, `registryFailure`).
- **Callback приложения** (`finishSignIn` из `@outegro/bff/sign-in`) сверяет state с `og_sso` как всегда. Удачная тихая попытка ставит `og_silent=silent`, вход по просьбе человека снимает маркер. Неудачная тихая попытка (`error`, отказ в обмене кода, сбой) возвращает на `returnTo` без сессии и без страницы ошибки; `tried` остаётся (на сутки после повторяющегося отказа). Callback, не совпавший по state, при `og_silent=tried` или уже имеющейся сессии (параллельные попытки вкладок, восстановленных вместе) ведёт на стартовую страницу без ошибки и не трогает `og_sso`, если ожидающий вход тихий или его нет; при входе, о котором человек попросил (две вкладки входа, долго на странице входа id), и в остальных случаях — страница ошибки, как раньше.
- **pay-web и admin-web** тихий вход не включают: все их страницы, кроме SSO и страниц после выхода (`/signed-out`, `/sign-in`), и так ведут на `/auth/sign-in`, а `/authorize` при сессии id выдаёт код без страницы входа. Страницы после выхода и после простоя admin остаются выбором человека.

Negative tests: `packages/bff/src/{proxy,sign-in,sso,bff}.test.ts`, `apps/id-web/src/lib/authorize.test.ts`, `apps/{battleship,edu}-web/src/lib/silent-sign-in.test.ts`; в браузере — блок «silent sign-in» в `apps/battleship-web/e2e/auth.spec.ts` (fake platform отвечает `login_required` без cookie персоны).
