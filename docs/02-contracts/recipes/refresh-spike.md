# Checkpoint ID-03: решение refresh concurrency

Здесь намеренно нет самодельного криптографического протокола. Задача модели — выбрать и проверить совместимое решение по актуальным библиотечным документам и записать точный contract. До этого она не меняет replay policy произвольно.

## Входные сценарии

1. Одно приложение обновляет access token обычным запросом.
2. Две вкладки одновременно используют одну предыдущую refresh version.
3. Два backend процесса одновременно обслуживают ту же family.
4. Server завершил rotation, client не получил response и повторяет.
5. Злоумышленник повторяет старый token вне допустимого retry contract.
6. Logout/revoke/suspend происходит одновременно с refresh.

## Что записать до реализации

- Family/token version states и точные атомарные переходы.
- Где хранится hash, где находится revocation authority.
- Чем доказывается допустимый retry и как ограничивается возврат прежнего результата.
- Что доступно после lost response и как долго; нельзя бессрочно принимать старую version.
- Как синхронизируются два процесса. Local single-flight решает только один процесс.
- Какие ошибки видит client; когда family отзывается целиком.
- Какие поля не попадут в logs и какое содержимое short-lived cache требует защиты.

## Порядок работы

Сначала написать state transition table и integration harness с двумя callers и управляемым Clock. Затем реализовать один atomic rotation operation. Потом добавить client/BFF retry. В последнюю очередь включать глобальную reuse response. Это не повод временно убрать защиту от reuse в production.

## Приёмка решения

Все шесть сценариев имеют однозначный ожидаемый outcome и воспроизводимый test. Legitimate retry не вызывает случайный logout; настоящий запрещённый reuse не создаёт новую session. Revoke всегда выигрывает последующую sensitive authorization. Если выбранная library не поддерживает нужную модель, ADR показывает ограничение и другой вариант, а не force override.
