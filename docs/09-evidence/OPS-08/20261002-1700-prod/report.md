- Статус: TC-OPS-08-01 и TC-OPS-08-03 — pass; TC-OPS-08-02 — pass по конфигурации, живой проверки нет.
- Task card: [OPS-08](../../../04-delivery/07-operations/tasks/OPS-08.md)
- Environment: production, один узел: 5 vCPU, 7,7 ГиБ RAM, allocatable 6,5 ГиБ, K3s v1.36.4 (`system-reserved` и `kube-reserved` по 512 МиБ, eviction при `memory.available < 200Mi`). Образы `3f91685`, gitops `bdd3181`/`ae01351`. Данные — Prometheus кластера.

## Профиль памяти (3 дня до теста)

- MemAvailable узла: медиана 1,8 ГиБ, минимум 761 МиБ (во время полной выкатки), за 4 часа с пятью полными выкатками — минимум 1110 МиБ.
- Сумма requests 3,8 ГиБ; лимиты превышают allocatable (лимиты — потолки контейнеров, не резерв).
- Пики контейнеров: argocd-application-controller 685 МиБ, prometheus 673 МиБ, **landing-web 504 МиБ при лимите 512 МиБ**, hermes 448 МиБ, grafana 320 МиБ, остальные сервисы платформы 85–200 МиБ.

## TC-OPS-08-02 Agent pressure — pass по конфигурации

- Hermes ограничен: requests 256 МиБ, limit 1 ГиБ — выше лимита его убивает OOM, соседей это не задевает.
- PriorityClass (gitops `bdd3181`): `outegro-core` (100000) у всех Deployment и StatefulSet платформы и у кластера PostgreSQL; `outegro-agents` (−1000, `preemptionPolicy: Never`) у Hermes. При нехватке памяти kubelet вытесняет поды сверх requests в порядке приоритета: Hermes первым, сервисы платформы последними.
- PostgreSQL: `priorityClassName` записан в Cluster, но CNPG применит его при следующем перезапуске инстанса; специально базу ради этого не перезапускали.
- Живой проверки (Hermes на своём лимите под нагрузкой) нет: не проводилась, чтобы не устраивать давление памяти в production.

## TC-OPS-08-03 Rollout — pass

- Rolling update всех девяти приложений одновременно (по одному лишнему поду на Deployment) за 3 дня опускал MemAvailable не ниже 761 МиБ; за 4 часа 02.10 с пятью полными выкатками — не ниже 1110 МиБ. До порога eviction (200 МиБ) запас больше 500 МиБ, Recreate не нужен. Hermes выкатывается Recreate (PVC RWO).

## Найдено и сделано

1. **landing-web у предела памяти.** Куча V8 ограничена (`--max-old-space-size=192`), а рабочий набор доходил до 504 из 512 МиБ, был один OOMKilled (30.09) и одно завершение с `Error` (01.10): остальное — нативная память sharp/libvips на glibc. Сделано: `MALLOC_ARENA_MAX=2` (gitops `aa10815`), в `next.config` один поток libvips, без кэша операций, последовательное чтение (`e242da5`). Локальный замер холодной оптимизации 73 вариантов картинок: пик 206 → 198–202 МиБ (Windows, эффект фрагментации там не воспроизводится). Проверка — рабочий набор landing в Prometheus в ближайшие дни (до изменений: пики 305–504 МиБ).
2. **Логи части подов терялись.** `fs.inotify.max_user_instances = 128` на узле, занято 144 (K3s ~60): kubelet не может следить за лог-файлами, и Alloy отправляет в Loki «failed to create fsnotify watcher: too many open files» вместо строк подов. В скрипте узла (gitops `a5d4ecd`) лимиты 8192 / 524288. На работающем узле не применено — нужно разрешение владельца на `sysctl` на сервере.
3. **RabbitMQ не переживал перезапуск** (найдено при выкатке приоритетов, см. инцидент в [отчёте R-05](../../R-05/20261002-1700-prod/report.md)): исправлено `fsGroupChangePolicy: OnRootMismatch` и init-контейнером (gitops `ae01351`).
